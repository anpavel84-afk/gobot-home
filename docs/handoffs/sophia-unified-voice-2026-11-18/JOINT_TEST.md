## Три шага этого прогона

Порядок ниже задан владельцем и имеет приоритет над предыдущим расширенным
сценарием. После первого ответа сначала разбираются события и слышимое качество.
При сбое сохраняются свидетельства и проверяется расход перед новой попыткой.

1. **Непрерывная короткая фраза.** После сообщения оператора «готов» произнести
   один раз: **«София, сколько будет два плюс три?»** Без отдельной паузы после
   имени. Ожидается пять, целый ответ и возврат к готовности/слушанию.
   Владелец сообщает, что услышал, были ли паузы или обрыв. До разбора этой
   попытки не переходить ко второму вопросу и не перезагружать устройство.
2. **Имя с паузой.** После отчёта оператора произнести «София», сделать
   естественную паузу, затем «Сколько будет четыре плюс шесть?» Ожидается
   десять; отдельное имя не должно расходовать ответ или терять начало вопроса.
3. **Полная экспертная цепочка.** Быстрый разговор → кешированный клип marin →
   эксперт Antigravity → диктор marin → уточняющий вопрос. Аналитическую задачу
   без требования свежего веб-поиска задаёт владелец. Проверить одно принятие
   задания, раннее содержательное озвучивание, единственный владелец аудио,
   целостный ответ и контекст уточнения после фактического окончания речи.

Перед каждым шагом проверяются оставшееся время и счётчики. При истечении
или исчерпании работа останавливается с конкретной причиной; счётчики не
восстанавливаются. Другие сценарии полного поручения, в том числе длинная
прямая диктовка, остаются отдельными незавершёнными пунктами общей приёмки.

## Обязательный отчёт после первой фразы

| Точка | Доступное свидетельство |
| --- | --- |
| Wake получен на PLAN | `wake_accepted.wake_received_monotonic` |
| Ввод допущен | `wake_accepted.plan_monotonic` |
| Endpoint | `endpoint_decided.plan_monotonic` |
| Первый PCM ответа | `first_audio_packet.plan_monotonic` |
| Первый пакет к колонке | Gateway `first_packet_sent_monotonic` |
| Начало цифрового вывода | `speaker_sound_started` / `driver_submit_receipt_monotonic` |
| Получено физическое окончание | `playback_receipt_received.plan_monotonic` |
| Услышанный контекст зафиксирован | `heard_context_committed.plan_monotonic` |

В отчёте указываются интервалы между точками, один фактический trace и версия.
По одному наблюдению не рассчитываются p50/p95. Начало I2S submit — цифровой
признак, а не акустическое измерение. Время ESP нельзя напрямую вычитать из
времени PLAN; USB хранит исходное время детектора и время прибытия отдельно.

Проверка отдельного имени измеряется по
`wake_fragment_pending → wake_fragment_question_ready`. Отсутствие pending
означает, что эта ветка для данного endpoint не применялась. Разница с
гипотетическим запуском без неё по одной попытке не доказывается.

Gateway сохраняет до двух ответов, до 64 progress-точек на ответ: minima/maxima
очередей decode/output, пустые очереди, output_in_flight, максимальные интервалы
отправки пакетов и progress-квитанций. Пустая программная очередь может
сосуществовать с заполненным DMA и сама по себе не доказывает underrun.
**В установленной прошивке hardware underrun не измеряется: значение null,
а не ноль.** Отдельно проверяются `max_output_tokens`, отмена и сетевой разрыв.

Для подтверждения контекста требуются одинаковый SHA response, роль
`fast_answer`, `heard=false` в принятой физической квитанции и последующий
`heard_context_committed` с `heard=true`. Получение только segment/cue/stale
квитанции не считается завершением содержательного ответа. Событие старого
`playback_finished` публикуется после обработки контекста, поэтому для порядка
используется новое событие получения квитанции. Ошибка записи и повтор квитанции
не должны создавать ложный маркер успешного commit.
