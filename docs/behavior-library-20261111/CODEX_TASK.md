# GoBot Home — внедрить библиотеку бытового поведения

Ты продолжаешь существующий GoBot Home на PLAN. Пользователь просит, чтобы обычный GPT Live уверенно выполнял стандартные бытовые сценарии и естественно обрабатывал продолжения. Эта задача авторизует внедрение спецификации в существующий проект; она не расширяет доступы, не выдаёт новые платные квоты и не разрешает прошивку устройства.

## Сначала установи фактическую точку работы

Рабочая директория: `C:\Users\PLAN\gobot\GoBotHome`. Прочитай действующий `AGENTS.md`, `docs/CURRENT_STATUS.md`, `docs/GOBOT_HOME_TARGET_SYSTEM.md`, `docs/REQUIREMENTS_MATRIX.md`, проверь HEAD и незакоммиченные изменения. Сохрани чужую/текущую работу. Пакет подготовлен по GitHub `effd1ff7be7150683ffacb0fa69934fd46142e87`; это не команда checkout. Старый `4931c49` не является текущей базой и не нужен для отката. Если HEAD ушёл вперёд, перенеси требования на текущую реализацию и не ломай уже исправленное.

Прочитай `README.md`, `SOURCE_AUDIT.md`, `scenario-library.json`, `dialogue-cases.json`, `fixtures.json`, `dialogue-rules.json` и `capability-map.json` из этой папки. Здесь 400 расширенных исходных сценариев и 120 дополнительных цепочек. Поля `capability_status` — оценка спецификации, не runtime-разрешение. Все `execution_evidence` изначально `not_run`.

## Обязательные границы

- Сохранить единый Brain и существующие C/A/B. Обычный C использует текущую утверждённую связку Live+Luna; A остаётся экспертным разговором; B и сравнительные URL сохраняются.
- Сохранить ограничения Luna, текущие разрешения и счётчики. Никаких новых моделей, скрытого LLM-классификатора, автоматических retries, платного аудио или ImageGen ради прохождения этих проверок.
- Каталог не выдаёт ACL, voice identity, private-memory или device-settings права. Гость и личный контекст остаются раздельными; смена profile epoch инвалидирует историю/задачи по действующим правилам.
- Не копировать демонстрационные погодные данные, таймеры, людей и прочие значения в рабочую базу. Все fixtures только в тестах.
- Не открывать shell из голоса; не изменять глобальную среду, сеть или сторонние проекты.

## Реализовать в первую очередь

1. **Подключить структурированную библиотеку.** Сохранить existing IDs и исходный inventory. Предпочтительно companion-файл/модуль и обратная совместимость; обновление схемы — только с loader/validator. В runtime выбирать небольшой набор нужных правил по домену/intent/context, а не вставлять все 400 карточек в prompt. `scenario-library.json` содержит примеры и acceptance, которые не должны все отправляться модели.
2. **Погодный диалог.** Разовый запрос другого города отделить от home setup. Сохранять `place/date/timezone/metric` в scoped RAM; поддержать «а завтра?», «а ветер?», «а в Рио?», «нет, в пятницу» без потери предмета. Существующий home/default и исправления дат сохранить. Не спрашивать уже известный город, не менять дом разовым запросом. Проверять горизонт и фактические поля источника.
3. **Распознавание неподключённых действий.** Перефразы музыки, света, календаря и напоминаний должны проверять registry, а не бесконтрольно уходить в текстовый backend. Не выполнять отрицания/цитаты/обсуждения команды. Для изменяющих действий использовать контролируемую полную грамматику и валидацию слотов; разговорную нормализацию не превращать в неограниченный fuzzy parser.
4. **Уточнение и отмена.** Одно missing-slot действие в текущем scope, одна понятная реплика. «Нет, спасибо» отклоняет ожидающее предложение; «отмени таймер» выбирает таймер; «стоп» сохраняет семантику End и не удаляет сохранённые таймеры. Текущие backend/expert jobs отменяются и очищаются по существующей политике закрытия сессии. Не считать «подробнее» согласием на CLI.
5. **Единственность исполнения и результат.** Существующий native-input path и client delegation используют одну operation claim. Дождаться допустимого input-end/answer evidence. Реальный delegation ID сохранить, выдуманный не создавать; app-initiated commentary идёт по существующему контракту. Поздние/повторные события не создают повторный таймер, отменённый/исправленный результат не озвучивается.
6. **Честные ответы и экран.** Отображение и речь берутся из одного result ID. Успех только после результата, `unknown/partial/failed` — отдельные ответы. Нет изображения — speaking face по действующим правилам; настоящие погодный/таймерный виджеты не заменять декоративной картинкой.

## Следующая часть после стабилизации

Расширить timer lifecycle именами, паузой/возобновлением и продлением только вместе с моделью данных, миграцией, реальным исполнителем и проверкой восстановления. До этого соответствующие команды честно сообщают ограничение. Абсолютные будильники, напоминания, календарь, музыка и умный дом требуют готовых scheduler/adapters и доставки. Их отсутствующие зависимости фиксировать отдельно; они не должны останавливать исправление уже доступных погодных/таймерных действий.

Будильник/таймер `due` не равен услышанному сигналу. При закрытом браузере/недоступном endpoint не обещать гарантированное звучание. Хранение и доставка проверяются раздельно.

## Проверки без платных вызовов

Сначала запусти `python validate_package.py` в папке пакета. Затем сделай test adapter к действующим обработчикам Brain: настоящая маршрутизация/валидация/SQLite и fake external IO, фиксированные часы, контроль числа вызовов и side effects. Не реализуй adapter как возврат `case.expected`.

`dialogue-cases.json` задаёт пользовательские, системные, provider и lifecycle события. `fixtures.json` задаёт базовое синтетическое состояние; `given_overrides` рекурсивно накладывается, массивы заменяются. События не превращаются в пользовательские фразы. Для timezone fixtures используй IANA зоны и календарные даты. При time shift в кейсах уже заданы свежие synthetic payload timestamps.

Каждый тест должен проверять реальные slots, scoped состояние, число/идентичность вызовов исполнителя, изменения объектов, факт/фазу ответа и screen result. Отдельно проверять input-end gating, replay, исправление даты, профиль и отсутствие нужного адаптера. Для части будущих positive fixtures ставить явный `blocked:not_implemented`, а не успешный прогон пустого обработчика. Проверка ожидаемого честного отказа может пройти отдельно.

`check_trace.py` сравнивает только нормализованный структурированный итог; semantic assertions из текста и акустическая проверка остаются отдельными. Сформируй собственные holdout-перефразы, не добавляй их заранее в runtime словарь. Обязательный набор: W001–W006, W011–W021, W047–W049, W056–W069, T001–T010, X001–X002, X006–X010, C001–C005.

Никаких новых Live/Luna/CLI/ImageGen прогонов без действующего разрешения именно на automated developer acceptance. Старые grant IDs и потраченные лимиты не обнулять. Ручное iPhone разрешение не использовать для автоматического набора из 520 вызовов.

## Что считать завершением

- Исправления включены в реальный путь C, а не существуют отдельной демонстрацией.
- Сохранены A/B, текущие действия, визуализация, ACL и бюджеты.
- Нет ложных подтверждений и повторных эффектов в принятых P0; weather home/temporary place/date/metric работают согласованно.
- Для каждого сценария отчёт различает `specified`, `implemented`, `offline_pass`, `provider_verified`, `browser_verified`, `iphone_acoustic_verified`, `hardware_verified` и точную блокирующую зависимость.
- В `docs/CURRENT_STATUS.md` и `docs/REQUIREMENTS_MATRIX.md` внесены фактические изменения, commit/runtime, покрытие и ограничения. Не создавать второй конкурирующий паспорт.
- Пользователю дан короткий отчёт: что реально исправлено, что прошло какими проверками, что требует интеграций и что он теперь может проверить голосом.

Не возвращай ещё один общий план вместо реализации доступной части. Выполняй работу по этапам, сохраняя явные блокеры для зависимостей; не объявляй весь каталог работающим по одному зелёному тесту.
