# GoBot Home — библиотека бытовых сценариев для Brain и GPT Live

Версия 1.0. Дата: 11 ноября 2026, America/Sao_Paulo.

## Назначение и результат

Этот пакет задаёт конкретное поведение домашнего GoBot: как понять естественную просьбу, уточнить недостающий параметр, выполнить доступное действие, сохранить контекст продолжения и сообщить фактический результат. Основной пользовательский путь — обычный разговор C через GPT Live. Экспертный разговор A остаётся отдельным режимом; более сильная модель сама по себе не добавляет доступ к устройствам, календарю или музыкальному сервису.

Пакет содержит 400 расширенных карточек из существующего каталога и 120 дополнительных проверочных цепочек. У исходных 400 карточек сохранены ID и канонические запросы; добавлены естественные перефразы, варианты ответа, слоты, предусловия, уточнения, ошибки, экранное поведение и критерии приёмки. Среди дополнительных цепочек 74 посвящены погоде, 20 — жизненному циклу таймера, 10 — будущим будильникам, напоминаниям и календарю, 16 — управлению разговором и взаимодействию подсистем.

**520 записей — объём спецификации поведения. Это не 520 реализованных навыков и не 520 успешно выполненных тестов.** Реальная готовность исполнителя, успешность текстовой проверки, прохождение настоящего сервиса, видимость на экране и слышимость на iPhone/ESP32 учитываются отдельно. Все данные испытаний вымышленные. Ни один пример не должен становиться настоящими домашними настройками или выдаваться за текущую погоду.

## Продуктовый стандарт

### Одно действие проходит один проверяемый путь

1. Принять завершённую реплику или настоящее событие делегации и связать их с одним `turn_id`.
2. Отделить команду от цитаты, отрицания, вопроса о команде и незавершённой транскрипции.
3. Определить домен и намерение существующими правилами, проверить слоты и допустимый контекст.
4. Проверить наличие исполнителя, область доступа, доступность источника и действующие разрешения.
5. Если не хватает параметра, задать один вопрос именно об этом параметре. Для полностью указанного обычного таймера не просить дополнительного подтверждения.
6. Исполнить действие через существующий Brain с одним ключом операции.
7. Сформировать речь и экран из одного фактического результата. Произнесённое «готово» не является доказательством успеха.
8. Сохранить только разрешённый контекст. Текстовую диагностику записывать лишь при действующем opt-in журнала привязанного владельца, в существующей зашифрованной области и с настроенным сроком хранения; иначе сохранять только разрешённые служебные метаданные.

Пример: «Поставь таймер» → «На сколько?» → «Пять минут» → запись таймера с длительностью 300 секунд → «Таймер на пять минут запущен» → виджет с тем же ID и сроком. Если запись не сохранилась, допустим только ответ о неудаче. Просьба «Поставь ещё один» в новом ходе создаёт отдельный таймер; повтор сетевого события того же хода — нет.

### Обычный разговор и эксперт

Текущая связка из инструкций проекта: C — `gpt-live-1` с `delegation.type=client` и утверждённым `gpt-6-luna` для общего текста; A — существующий STT/CLI/SpeechFormatter/TTS; B — сохранённая Realtime-сборка. Это описание конфигурации проекта на снимке, не рекомендация менять модели или заявление о новом API.

«Экспертный режим» переключает весь разговор в A. Разовая задача конкретному эксперту в C проходит существующий механизм jobs. «Расскажи подробнее» не означает согласие на запуск CLI. Недоступность календаря, лампы или музыкального сервиса не устраняется отправкой вопроса более сильной модели. Смена режима не должна терять уже сохранённый таймер или смешивать области персональных данных.

Сохранить ограничения Luna: суммарный вход не более 2048 токенов с подсчётом до генерации, выход до 512, `reasoning=none`, без tools и повторов, один запрос одновременно. Сюда входят инструкции, разрешённый контекст и сам запрос. Нельзя добавлять весь каталог в системный промпт, вводить скрытый классификатор LLM или автоматически повышать бюджет.

### Контекст хранит данные, а не обещания модели

Предлагаемая минимальная структура в существующем session state:

```json
{
  "scope": {"principal_id": "...", "device_id": "...", "client_id": "...", "conversation_id": "...", "profile_epoch": 1},
  "active_domain": "weather",
  "last_intent": "weather_query",
  "slots": {"place_id": "...", "timezone": "America/Sao_Paulo", "start_date": "2026-11-12", "end_date": "2026-11-12", "metric": "wind"},
  "pending": null,
  "selected_object_id": null,
  "source_result_id": "...",
  "input_revision": 3,
  "expires_at": "..."
}
```

Названия новых полей — предложение для интеграции, а не утверждение, что такая схема уже есть. Scope формируется доверенным сервером из действующей привязки сессии; значения клиента не могут расширять область доступа. Использовать существующие `tool_context`, `weather_last_request` и operation claim. Не создавать второй Brain или вторую базу профилей.

В рамках активного разговора разрешается наследовать предметно подходящие слоты: «а завтра?» меняет дату, «а ветер?» — показатель, «а в Рио?» — временное место. Любая смена профиля/прав, закрытие сессии или переход к несвязанной теме прекращает такое наследование. Для неочевидного продолжения задать короткий вопрос. Как консервативный стартовый параметр предлагается максимум 120 секунд с последнего относящегося к домену хода внутри той же активной сессии; это не отменяет существующее закрытие разговора после фактического завершения аудио и idle. TTL конфигурируется и проверяется отдельно.

Постоянный домашний город и временный город запроса — разные поля. «Погода в Рио» не является разрешением сохранять Рио как дом. Настройка дома использует существующие проверку владельца устройства, подтверждение места и верификацию источника. Координаты не передаются в Live как лишний контекст: достаточно разрешённого названия города, даты, единиц и результата.

### Погода

Показатели берутся из реального ответа источника. «Сейчас» использует текущие данные; «завтра» — нужную локальную дату; температура, вероятность дождя, количество осадков, ветер и порывы не подменяют друг друга. `null` не равен нулю. Для частичного ответа назвать доступный показатель и отсутствие другого.

Предлагаемая календарная политика: «на неделю» — семь локальных дат начиная с сегодня, с произнесённым диапазоном; «на следующей неделе» — следующий понедельник–воскресенье; «на выходных» — ближайшие соответствующие суббота и воскресенье с явными датами. На границах периода не отдавать прошедший день из текущего прогноза. Если намерение действительно неоднозначно, уточнить нужные даты.

Open-Meteo документирует до 16 дней для общего forecast endpoint, с зависимостью от модели и фактически возвращённых данных. При фиксированном сегодня 11 ноября шестнадцатидневное окно заканчивается 26 ноября включительно; 27 ноября за пределами этого окна. Проверять реальную последнюю дату и наличие нужного поля, а не только максимальное число в документации. Исторические, почасовые и морские данные могут существовать у провайдера, но наличие соответствующего адаптера GoBot проверяется отдельно. См. [документацию Open-Meteo](https://open-meteo.com/en/docs).

Сбой геокодера, timeout источника, HTTP 429, неполные данные и неподключённый провайдер имеют разные причины. Не говорить «нет интернета» без подтверждения. Кэш можно назвать только с временем обновления; просроченные данные не объявляются свежими. Коррекция «нет, завтра» инвалидирует предыдущий request revision, чтобы поздний ответ за сегодня не попал в речь или на экран.

### Таймер, будильник и напоминание

Таймер — относительный интервал. Будильник — локальная дата/время и зона. Напоминание — содержание, расписание и место доставки. Это разные сущности даже при похожих репликах. Для текущего таймера сохраняются действующие ограничения длительности; новые операции добавляются вместе с реальными переходами состояния и миграцией данных.

Для будущего расширения таймера нужны ID, необязательное имя, scope, целевое устройство, исходная длительность, deadline UTC, состояние `active/paused/expired/cancelled/dismissed`, остаток при паузе, версия записи и ключ операции. Пауза не удаляет таймер. Продление меняет тот же объект. «Второй» ссылается на актуальный объявленный пользователю список; произвольный порядок SQL не подходит.

Окончание Live не удаляет сохранённый таймер. Однако таймер, срок которого истёк на сервере, и реально услышанный сигнал — разные события. Закрытый мобильный браузер не даёт гарантии звучания. `due`, `alert_sent`, `client_received` и `audio_played` должны различаться; если устройство не подтвердило звук, статус доставки неизвестен. Для будильника нельзя обещать «разбужу» до готовности постоянного scheduler и подтверждённого канала доставки. Наличие будущего сценария в JSON не включает эту возможность.

Голосовое «стоп» сохраняет уже утверждённое завершение разговора и прекращение текущего звука; оно не удаляет сохранённые таймеры. Текущие backend/expert jobs отменяются и очищаются по существующей политике закрытия сессии. Если одновременно звучит сигнал, его можно приглушить/закрыть по отдельному явному правилу, сохранив остальные расписания. Простое перебивание ответа с продолжением беседы не равно End. «Отмени таймер», «не надо эксперта» и «отмени уточнение» имеют собственные цели. Новые приоритеты нельзя молча подменять поверх текущего поведения A/C.

### Настоящие результаты и ошибки

Для ответа нужен нормализованный результат существующего исполнителя. Предлагаемые поля:

```json
{
  "operation_id": "...",
  "turn_id": "...",
  "profile_epoch": 1,
  "capability": "timer",
  "phase": "succeeded",
  "effect_applied": true,
  "result": {"timer_id": "...", "duration_seconds": 300, "deadline_utc": "..."},
  "error_code": null,
  "source_result_id": "..."
}
```

Фазы `accepted`, `succeeded`, `partial`, `failed`, `cancelled` и `unknown` различаются. `accepted` значит лишь принятие задания. При `unknown` нельзя произносить подтверждение или автоматически повторять изменение. Сначала, если это безопасно и предусмотрено адаптером, прочитать статус той же операции. Это не разрешение на новые платные попытки или повтор передачи команды.

Минимальные классы ошибок: `unsupported`, `not_connected`, `not_authorized`, `needs_clarification`, `not_found`, `ambiguous`, `invalid_argument`, `unreachable`, `source_timeout`, `rate_limited`, `stale_data`, `storage_error`, `partial_success`, `cancelled`, `unknown_outcome`. Причина остаётся точной в диагностике; голосовой ответ короткий и понятный. Не озвучивать stdout, полный provider error, внутренние промпты или секреты.

## Как использовать варианты ответа

Варианты в карточках — примеры допустимой речи с одним смыслом, а не случайный общий список. Для точных действий Brain определяет факты и допустимую фазу; Live произносит короткий результат. Для объяснений Luna формирует ответ по выбранному контракту и запросу. Пример из карточки не обязан навсегда стать единственной дословной формой.

Три правила:

- Шаблон успеха допустим только после успешного результата. «Пробую», «запущено» и «готово» нельзя смешивать в одном наборе.
- Переменные `{result.*}` заполняются валидированным результатом. Неизвестное значение не дополняется из воображения; выбирается ветка частичного ответа/сбоя.
- Уточнение не спрашивает то, что уже известно. Имя города, время, название таймера и единицы переносятся из разрешённого активного контекста.

Экран отображает тот же объект и данные, что речь. Для изображений сохраняется существующий speaking face до появления реально декодированного медиа; отправленная scene не доказывает показ. Погодный и таймерный виджеты остаются настоящими виджетами. Демонстрационные значения из 192 дизайн-макетов в runtime не попадают.

## Порядок внедрения

### Этап 1 — поведение существующих действий

Загрузить companion-каталог без замены исходных ID. Добавить строгую валидацию данных. Исправить разовый город/metric/date context, aliases неподключённых действий, clarification state, отмену и единственность операции. Приёмка: W001–W006, W011–W021, W047–W049, W056–W069, T001–T010, X001–X002, X006–X010, C001–C005. Это приоритет для нормального обычного разговора; он не требует появления Spotify или умного замка.

### Этап 2 — таймеры и постоянные события

Дополнить модель таймера именами, паузой, продолжением и продлением только вместе с миграцией, scheduler и честной доставкой. Отдельно решить постоянные будильники/напоминания. До готовности новые positive-fixtures остаются `blocked/not_implemented`; тест честного ограничения может пройти отдельно. Не объявлять всю категорию готовой по одному успешному созданию.

### Этап 3 — подключаемые возможности

Музыка, умный дом, календарь, списки и внешние сервисы получают реальные адаптеры, scoped разрешения и результаты. Наличие сценария задаёт желаемое поведение, но не предполагает уже оплаченный сервис, аккаунт, подписку или разрешение на отправку сообщения/покупку. Внедрять по фактической готовности оборудования и доступов; не блокировать этап 1 из-за этих зависимостей.

### Этап 4 — речевая и экранная приёмка

Сначала без оплаты: реальные обработчики Brain с fake IO, фиксированными часами и состоянием; затем контролируемые браузерные проверки. Реальные Live, Luna, CLI и ImageGen прогоны только в пределах актуального отдельного разрешения. Старые израсходованные developer grants нельзя использовать повторно. Ручное разрешение владельца на его телефон не превращается в разрешение на автоматический платный прогон.

Финальная проверка пользователя: тихая человеческая речь, естественные перефразы, исправление на ходу, прерывание, фоновые звуки, разрыв сети, закрытие браузера, реальный таймер и круглый экран. Эти результаты нельзя получить проверкой JSON или одной синтетической озвучкой.

## Контракт проверки

`validate_package.py` проверяет артефакт: количество, обязательные поля, уникальность ID, сохранение канонических запросов, наличие речевых вариантов, корректность структуры fixtures и отсутствие ложных статусов `passed`. Это не запускает GoBot и не доказывает поведение.

`check_trace.py` принимает ID из `dialogue-cases.json` и JSON нормализованного trace от будущего test adapter. Поле `expected` сравнивается рекурсивно; списки сравниваются точно. Специальные ключи `*_lte` и `*_max` — верхняя граница соответствующей метрики. Например `luna_input_tokens_lte: 2048` требует числовой trace `luna_input_tokens <= 2048`. Адаптер должен собирать реальные изменения БД, вызовы исполнителя и сообщения renderer, а не возвращать ожидаемый JSON. Проверку смысла речи, истинности источника и фактического воспроизведения автоматическое сравнение структур не заменяет.

Для P0 требуется ноль ложных подтверждений, ноль повторных изменений от одного хода, ноль передачи приватных данных между областями. Для каждого поддержанного сценария должны совпасть route, slots, effect, речь и экран; для неподключённого — точная причина и отсутствие изменения. Нужны отложенные перефразы, которых нет в обучающей части каталога, и реальные пользовательские формулировки после их явного разрешения на диагностику.

В `docs/CURRENT_STATUS.md` и `docs/REQUIREMENTS_MATRIX.md` записать только фактические изменения и доказательства. Этот пакет — задание и набор контрактов, он не заменяет паспорт проекта. Не переписывать историческую статистику 3 Live/10 Luna и старые суммы; новые измерения учитываются отдельно.
